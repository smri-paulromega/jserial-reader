# Contributing

Thanks for helping. This is a small tool, and these rules keep it that way.

## Ground rules

- **Java 8 source level.** No `var`, records, text blocks, `switch` expressions, `List.of()`, or any API
  added after Java 8. The build compiles with `--release 8`, so it catches newer APIs.
- **No dependencies.** The tool must stay one jar that runs with plain `java -jar`.
- **Never deserialize.** Don't call `ObjectInputStream.readObject()`, and don't load or instantiate
  classes named in the stream. This is what makes the tool safe on untrusted data (see
  [SECURITY.md](SECURITY.md)).
- **Exact numbers.** `BigDecimal` values must print with their original scale. Don't add rounding.
- **No real data.** Don't put real blobs, real names, or account numbers in issues, tests, commit
  messages, or examples. Make a synthetic blob (see below).
- **Style:** tabs for indentation, and match the surrounding code. `.editorconfig` sets this up in most
  editors.

## Build and test

You need a JDK 8 or later. On Windows, run the `.sh` scripts from Git Bash.

```sh
sh build.sh    # -> build/jserial-reader.jar   (build.cmd on Windows)
sh test.sh     # regression tests; must print "All tests passed."
```

`test.sh` runs the jar on [`src/test/resources/sample.hex`](src/test/resources/sample.hex) and compares
the result with [`sample.expected.txt`](src/test/resources/sample.expected.txt). It also checks the
error paths and exit codes. CI runs it on Java 8, 11, 17 and 21.

## Changing the test fixture

`sample.hex` is generated by
[`SampleBlobGenerator`](src/test/java/jserialreader/SampleBlobGenerator.java), and every value in it is
made up. To cover a new type, add it to the generator, then regenerate both files:

```sh
mkdir -p build/test
javac --release 8 -d build/test src/test/java/jserialreader/SampleBlobGenerator.java
java -cp build/test jserialreader.SampleBlobGenerator > src/test/resources/sample.hex
sh build.sh
java -Duser.timezone=UTC -jar build/jserial-reader.jar -f src/test/resources/sample.hex \
  | tr -d '\r' > src/test/resources/sample.expected.txt
```

**Read the diff of `sample.expected.txt` before you commit it.** The expected output is only worth
something once a person has checked that it's correct.

## Pull requests

1. Fork the repo and create a branch from `main`.
2. Make the change, and add a test for it in `test.sh` or the fixture.
3. Run `sh test.sh`.
4. Add a line under `## [Unreleased]` in [CHANGELOG.md](CHANGELOG.md).
5. Open the pull request. CI must pass.

[GNU GPL v3 or later](LICENSE), the same license as the project.

## Releasing (maintainers)

1. Update `VERSION` and move the `[Unreleased]` entries in `CHANGELOG.md` under the new version.
2. Commit, then tag the commit and push the tag: `git tag v1.2.0 && git push origin v1.2.0`.
3. The release workflow builds and tests the code, then publishes the zip, the tar.gz and `SHA256SUMS`
   on the Releases page. The tag must match `VERSION`.
